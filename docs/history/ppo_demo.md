# 三维 PPO 局部动态避障原型演示

## 原城市环境与三个移动障碍

```bash
scripts/run_ppo_city_demo.bash --gui --scenario 1
```

城市入口现优先使用本工作区的 `runs/direct_ppo_3d/city_training/city_demo_model.zip`（与静态城市阶段 75,000 步检查点相同的冻结模型）。同一模型在真实城市中，场景 1 初测及两次重启复测共 **3/3 完成往返降落**，最小激光读数分别 1.115、1.250、1.121 m；场景 3 也通过，场景 2 仍触发保护。两版额外混合障碍训练没有产生更可靠的候选，因此保留这个已实飞的演示模型。详细过程见 [城市训练记录](city_ppo_training.md)。它是演示原型，尚未达到多场景泛化验收。

模型不存在时城市入口回退到旧模型；用 `--model` 可明确指定模型，运行目录中的 `demo_config.json` 记录实际加载模型的 SHA-256。模型按项目约定不纳入 Git。

无桌面环境将 `--gui` 改为 `--headless`。脚本保留原 `logistics_city.sdf` 的六栋建筑、树木、道路、包裹、起降区和已有移动球，生成 `logistics_city_ppo.sdf` 并加入 Gazebo 内部激光跟随插件。原城市文件不修改，生成器会逐项保留场景元素。

沿南侧起降区前方的 28 m 航线新增红、橙、紫三个绕圆运动的球体，航线从 `(-34,-23,6)` 到 `(-6,-23,6)`，然后返回降落。场景编号改变三个球体的轨道、初始相位和速度；每次使用相同场景编号也可能因启动耗时而有不同的交汇时刻。`--obstacles 1` 可退回单障碍，`--corridor-length` 调整 6–30 m 航线（三个障碍时至少 24 m）。原城市已有的移动球保留在中心区域，因此场景中总计四个移动球，新增的三个位于本次航线上。

城市入口等价于 `scripts/run_ppo_demo.bash --environment city`，也支持 `--model`、`--output-dir`。只启动 1 号机任务，其余两机保持停机；不是三机并发运输，也不是城市全局路径规划任务。近障碍时 PPO 输出三维速度，远处/末端的目标跟踪和安全保护职责与实验场一致。

城市环境会将建筑和树木的实际激光回波输入当前策略。新候选已加入静态城市训练，混合障碍泛化仍未达标；遇到过近障碍或失效仍触发原有中止降落条件，不放宽验收。

初始旧模型的一次真实城市闭环试飞，结果位于 `runs/direct_ppo_3d/city_three_obstacles_s1_v1/`：Gazebo 场景查询确认六栋建筑、六棵树、原移动球和新增三球模型实际存在；新增三个球体的记录位置变化分别超过 5.12、6.15、4.11 m，确认在运动。任务结果为 **FAIL**：无人机在约 `(-12.65,-23.19,3.57)` 的原有树木附近持续制动，未在巡航 60 s 内到达目标，触发超时降落。最小激光读数 1.292 m，未触发 0.8 m 连续低净距条件；PPO 接受 98 个周期、安全制动 469 个周期、势场控制 0 个周期。城市接入可运行，不等于现有模型已通过城市任务验收；本轮城市训练与后续模型选择记录在上方链接中。

每次运行保存 `world.sdf`、模型、三球 SDF、`spawn.json` 实际生成确认、位姿与控制日志、结果和包含城市建筑的诊断图。批量城市验证：

```bash
python3 scripts/validate_ppo_demo.py --environment city --scenarios 1 2 3
```

## 一键运行

在项目目录执行：

```bash
scripts/run_ppo_demo.bash --gui --scenario 1
```

无桌面环境执行：

```bash
scripts/run_ppo_demo.bash --headless --scenario 1
```

脚本启动 Gazebo/PX4、激光处理、PPO 推理和单机任务，任务结束后生成轨迹图并清理启动的进程。UAV 2/3 保持停机。`--model` 可指定本地模型，`--output-dir` 指定新的结果目录。

## 批量复测

```bash
python3 scripts/validate_ppo_demo.py --scenarios 1 2 3 --repeats 2
```

逐次重启仿真，避免多个任务争用同一 PX4/Gazebo。每次保存完整结果，批次根目录的 `validation.json` 分别报告任务完成与激光净距审查。默认审查要求巡航日志中每一个有效激光最小值均不小于 0.8 m；单帧低于阈值也不通过审查。该审查比现有连续两帧才中止飞行的任务条件更严格，不改变飞行控制策略。进程失败、缺少生成确认或缺少有效巡航数据均不能通过。脚本会继续采集剩余场景，任意一次未通过时最终返回非零退出码。

激光读数是传感器到可见物体的射线距离，不能当作机体表面到障碍物的真实最短距离。新增 `control_trace.csv` 的完整 36 扇区、观测年龄和主机单调时间，以及 `gazebo_poses.jsonl` 中的实际仿真位姿，供低读数复查；球体 link 位姿相对于障碍模型，分析时须按父模型变换，不能直接当世界坐标。位姿记录不输入 PPO 或控制器。

启动流程会等待激光话题就绪，避免世界服务已就绪而传感器尚在初始化时过早启动激光桥接。

当前默认模型：`runs/direct_ppo_3d/dynamic_gazebo_lidar_route_v1/best_model.zip`。模型文件按项目约定不纳入 Git；本工作区已有。每次演示会复制模型为 `policy.zip` 并保存 SHA-256，避免结果只依赖可变路径。

## 场景与控制职责

- `ppo_avoidance_lab.sdf`：地面、起降区、激光；无城市建筑、树木或额外障碍。
- 12 m 往返走廊，一个实际生成并运动的球体，处于当前训练距离范围内。
- 启动前确认 Gazebo 场景中确有目标模型，记录 `spawn.json`；不仅依赖创建请求的 Boolean 返回值。
- 虚拟激光保持水平，安装在机体上方 0.6 m；向下传感器在机体下方 0.4 m，与新训练射线模型一致。
- 演示世界通过 Gazebo 内部 `mupt::SensorFollower` 每个仿真步更新激光安装位置；ROS 节点只发布实际激光位姿的 TF。启动脚本自动编译插件（需要 CMake、C++ 编译器、`gz-sim8` 和 `gz-plugin2` 开发库，本机已具备），编译日志保存在 `plugin_build.log`。城市世界默认仍采用原接口。
- 远处使用全局目标速度跟踪（`route`）；探测到 6 m 内障碍后，由 PPO 直接输出机体系前/左/上速度（`rl`）。保持至少 3 s，测距超过 8 m 达 15 个控制周期后可退出局部控制。
- PPO 命令通过方向制动、高度和向下净距保护。保护不生成势场引导速度。
- 返回最后 5 m 使用精确目标跟踪（`approach`）；起飞/降落仍是传统/PX4 控制。
- 演示模式不启动势场 advisory 节点，不将势场速度输入 PPO，也不与 PPO 速度相加。

这是局部控制原型，不能表述为全程由 PPO 单独完成所有控制。

此前 Python 跟随的场景 3 诊断中，单帧 0.681 m 时实际球体距激光原点至少约 4.425 m，说明那一次读数不能由目标球解释。不能据此推断所有低读数均虚假。旧诊断批次 `validation_margin_v1` 中还保留了启动失败，以及修改运行中 shell 脚本导致包装进程异常退出的记录；上述最新批次完整重启复测，不使用旧批次计算通过率。

本轮四个场景有 3 个通过、1 个失败，且每个仅运行一次，并非统计稳定性验收。模型泛化仍需要改进，现有默认模型保持原训练版本。默认场景 1 接受 PPO 103 个周期、安全制动 25 个周期，不能将全部飞行表现归因于 PPO 独立控制。

## 本次修正

1. 创建障碍时将输出/SDF 路径转为绝对路径，并增加实际生成确认。修复前几次使用相对结果目录的诊断试飞没有成功生成目标球；它们只能证明飞行接口，不能作为动态避障能力证据。原始失败数据保留。
2. 训练从宽角锥近似切换为 Gazebo 对应的 3×120 射线，再压缩为 36 扇区，纳入安装高度和地面。已用 Gazebo 中的已知球体实测，中层前向距离误差约 0.0011 m。
3. 增加无障碍训练回合和偏离路线的奖励代价，减少提前大幅绕行的捷径行为。
4. 将全局目标跟踪与 PPO 局部接管分开，分别记录控制来源，没有放宽已有近障碍交互和 PPO 控制周期判据。

## 当前限制与下一阶段

校准后模型的独立 1000 回合轻量测试为 92.9% 成功、6.1% 碰撞、1% 超时，未达到原定泛化门槛；轻量模型结果也不等于上述局部接管闭环结果。当前交付是可复现的单机、单动态障碍原型，不是复杂场景或多机避障系统的完成。

下一阶段应扩展重复场景、复核短时净距不足、改善模型泛化，再增加多个动态障碍和城市静态障碍。不要把两个成功例子当作批量通过。
